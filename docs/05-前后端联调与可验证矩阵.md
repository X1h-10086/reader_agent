# 05 · 前后端联调与可验证矩阵

> **一句话目标**：后端每一项能力，都能在前端被**触发**、被**看见**、被**验收**；每一个前端功能，都能反查到它依赖的**后端能力**与**后端测试用例**。
>
> 本文是整个项目「可验证性」的唯一规范。**前后端不是两套验收标准，而是同一张表。**

---

## 📖 白话速览：为什么要搞这套"看得见"的机制

**问题**：后端写完，自己点几下 Swagger 就说"做完了"；结果一接前端什么都不对，而且出问题根本看不出错在哪一步。

**办法**：给后端每一项能力装一个「仪表盘」——能在网页上**点一下就触发**，并看到**最原始的返回**（不是被美化过的结果）。

三个看的地方：
1. **业务页面**（给用户看）：等级色标、高亮、进度条；
2. **`/console` 探针台**（给你验收看）：每个能力一条，能触发、看原始 JSON、看耗时；
3. **响应/trace 抽屉**（每个页面右下角常驻）：HTTP 状态、请求与响应原文、经过了哪些节点。

> 一句话：**看得到中间过程，才叫看得懂后端。**

---

## 1. 四条硬性规则

| 编号 | 规则 | 执行标准 |
| --- | --- | --- |
| **V-01 后端为主** | 功能定义来自 `docs/03` 的能力与接口，前端只做呈现，不在前端发明能力 | 出现"前端能但后端没有"的能力 → 判定为设计缺陷，先补后端 |
| **V-02 不可观测 = 未实现** | 任何后端能力必须有一个前端观测点，否则不算完成 | 模块 DoD 中必须填写「前端观测位置」一行 |
| **V-03 契约先行** | 后端先出 OpenAPI 契约 → 前端自动生成 TS 类型 → 再各自实现 | 后端接口未定义前，前端不允许手写假接口 |
| **V-04 三位一体才算 Done** | **后端实现 + 前端观测 + 一条可执行测试用例** 同时完成 | 见 `docs/04` 的 DoD 扩展条款 |

> **反模式警告**：最常见的失败形态是"后端写完了自己在 Swagger 里点几下就算测过"，结果集成时前端什么都不对。本套机制就是为了避免它。

## 2. 可视化三层体系（前端作为观测面）

```
┌──────────────────────────────────────────────────────────────────┐
│ L1 业务视图（给真实用户）                                          │
│    上传页 / 审阅工作台 / 规则管理 / 任务中心 / 文档详情             │
│    → 用业务语义呈现结果：等级色标、高亮定位、进度条                 │
├──────────────────────────────────────────────────────────────────┤
│ L2 能力探针台 Capability Console（给开发/给自己验收）  ←★ 本文新增  │
│    /console：按模块列出全部后端能力，逐个「在线触发 + 看原始响应」  │
├──────────────────────────────────────────────────────────────────┤
│ L3 原始响应抽屉 + Trace 回放面板（每个页面右下角常驻）              │
│    HTTP 状态 / 耗时 / 请求体 / 响应体原文 / 本动作经过的节点序列    │
└──────────────────────────────────────────────────────────────────┘
```

**为什么要 L2 单独一层？**
因为 L1 会把结果"美化"，掩盖问题。比如检索召回了 8 条却因为 rerank 阈值丢了正确那条——在业务视图里你只看到"没找到"，只有在探针台里才能看到各阶段候选与分数。**看得到中间过程，才叫看得懂后端。**

## 3. L2 能力探针台详细设计（核心新增物）

### 3.1 页面布局

```
┌── /console ─────────────────────────────────────────────────────┐
│ 顶部：环境探针（.env 状态 / MinerU / DeepSeek / DB / 磁盘）       │
├───────────────┬──────────────────────────┬─────────────────────┤
│ 左：能力树     │ 中：单能力执行区          │ 右：响应观测区       │
│ M1 解析       │  能力说明 + 关联模块文档   │ HTTP 状态/耗时       │
│  ├ CAP-M1-01 │  参数表单（自动表单化）   │ 原始 JSON（可折叠）  │
│  ├ CAP-M1-02 │  [执行] [重置] [复制curl] │ 「前端影响」快捷跳转 │
│ M2 结构…     │  WS 事件流（实时）        │ Diff 上一次结果      │
└───────────────┴──────────────────────────┴─────────────────────┘
```

### 3.2 能力注册表（后端单一来源）

后端暴露一份元数据，前端**自动渲染**探测表单，避免每加一个能力都要改前端：

```python
# backend/core/capability.py
class Capability(BaseModel):
    id: str                 # "CAP-M1-01"
    module: str             # "M1"
    name: str
    target: str             # REST 路径 / WS 通道 / 内部函数名
    method: str             # GET|POST|WS|INVOKE
    params: list[ParamSpec] # 自动表单化：类型、默认值、是否必填、示例值
    hint: str               # 预期现象说明（喂给验收清单）
    related_view: str       # 触发后应去哪个业务页面看效果 → 实现 V-01/V-02

@router.get("/capabilities", response_model=list[Capability])
def list_capabilities(): return REGISTRY
```

> 前端只需写一次通用渲染器：`GET /capabilities` → 生成左侧树 + 中间表单 + 右侧响应面板。
> **新增后端能力 = 在后端注册一行，前端自动出现。** 这就是"以后端设计为主"的落地方式。

### 3.3 三个必备小面板（成本极低、价值极高）

| 面板 | 内容 | 解决的痛点 |
| --- | --- | --- |
| **环境健康** | `.env` 必填项是否齐全、MinerU/LLM 连通性、DB 版本、磁盘余量 | 出问题先区分是配置问题还是代码问题 |
| **WS 事件流** | 实时显示 `task.progress` / `need_human` / 节点进入退出事件原始帧 | 异步流程"看不见"导致无法调试 |
| **缓存与成本** | 本次命中了哪层缓存、消耗 token、LLM 调用次数 | 成本与延迟问题无法归因 |

## 7. 后端未完成时前端怎么办（Mock 策略）

原则：**Mock 只出现在 `/console` 与开发模式，不污染业务视图。**

| 手段 | 做法 | 用途 |
| --- | --- | --- |
| 契约文件 Mock | 由 OpenAPI 生成的 MSW handler，自动返回 schema 假数据 | 后端接口未实现时前端可先开发 |
| 固定夹具 fixtures | `frontend/mocks/*.json`（块结构、意见样例、trace 样例） | 演示与 UI 调试 |
| 开关 | `VITE_USE_MOCK=true`，页面角标显示「MOCK 模式」 | **必须醒目**，避免误判已联调成功 |
| 退出条件 | 某能力在 `/console` 走真实后端跑通即删除对应 Mock | 防止 Mock 长期滞留伪装进度 |

## 8. 执行节奏（与 `docs/04` 里程碑对齐）

每个模块开工时必须同时确定三件事，缺一不可：

```
① 后端能力函数/接口      → 写实现 + tests/api/test_mX_*.py
② /console 探针台条目    → 在 capability registry 注册一行
③ 业务视图观测点         → 在哪个页面能看到它、看到什么
```

`docs/04` 的 DoD 由此扩展为四条：**能力实现 ✓ → 探针可见 ✓ → 业务视图可见 ✓ → 用例通过 ✓**。

**推荐联调顺序**（先易后难、先确定性后随机性）：
M1/M2 观测（解析看得见）→ M3 规则（结果稳定最适合验证链路）→ M6 编排（加拓扑与中断）→ M5 LLM（带丢弃/复检面板）→ M4 知识 → M7 人工闭环 → M8 缓存与权限 → M10 评测 → M11 运维。

## 9. 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| 前端自己造了一套假数据 | 演示很顺，一接真实后端全崩 | Mock 必须带角标，且退出条件写进任务 |
| 只看业务视图验收 | 掩盖中间层错误 | 高等级能力必须在 `/console` 看原始响应 |
| 接口改了前端没同步 | 字段 undefined | OpenAPI 自动生成 TS 类型 + 契约测试 |
| 能力越来越多，探针台手写成百上千行 | 维护成本爆炸 | 后端元数据驱动 + 前端通用渲染器（§3.2） |
| WS 事件无统一格式 | 前端到处 `if-else` 猜字段 | 事件 schema 固定 `{type, task_id, seq, ts, payload}` |
| 异步任务失败静默 | 永远卡在 running | 每个节点 exit 写终态 + 前端心跳超时提示 |
| 手工测试只在功能写完时做一次 | 回归时全忘 | TC-01~TC-08 列为每期冒烟必跑 |
