# 04 · 工程目录结构与里程碑

> 本文回答：**代码怎么组织**（保证每个模块文档能在仓库里找到对应位置）、**分几期做完**（保证一直有可运行的东西）。

---

## 📖 白话速览：目录为什么要这么分

**四层就是一家餐厅**，谁也不能越界：

```
api     服务员 ← 接单、传菜，不自己做菜
service 领班   ← 安排流程：先做哪道、要不要退菜
domain  厨师   ← 真正干活：解析、切片、规则、审核
infra   仓库   ← 提供米面油和灶台（数据库、存储、外部 API）
```

为什么禁止"厨师去前台收银"（`domain` import `fastapi`）？
因为厨师一旦认识菜单，你想换一家餐厅（换框架/换界面），厨师就跟着失业。**厨师只认识食材，谁端盘子都不影响他做菜。**

对应到目录：`api/` 只写接口，`service/` 只写流程，`parsing/ representation/ rules/ agent/` 是厨师，`infra/` 是仓库。**放文件时先想"我是服务员还是厨师"。**

## 2. 依赖方向规则（防止代码腐烂）

```
api  →  service  →  domain(parsing/representation/rules/retrieval/agent)  →  infra
```

- 反向依赖禁止（如 `parsing` 不得 import `api`）；
- `domain` 不 import `fastapi`；
- `infra` 不知道业务语义；
- 跨模块只通过 `docs/03` 定义的数据结构通信，不互相 import 内部实现。

建议在 CI 里加一条 lint 规则自动检查越界 import。

## 3. 里程碑（每期都有可运行产出）

> 原则：**先纵切后横扩**。第一个里程碑就要有"上传→审核→出结果"的完整闭环，哪怕只能查一条规则。

### M0 · 骨架（0.5~1 周）
- 定义 `core/enums.py` 与 `Block/Chunk/Finding/Rule` 数据类
- FastAPI 起来，`/docs` 可用；前端能访问
- 搭建 Git 仓库、测试框架与 CI 流水线
- **产出**：一个空的但能跑的前后端

### M1 · 解析可用（1 周）
- MinerU 接通 + Adapter + 坐标归一化 + 质量评分
- 前端能看到解析结果与 PDF 对照
- **产出**：`上传 → 看到带高亮的结构化全文`（此时还没有 LLM）
- **同步**：`/console` 探针台上线，注册 CAP-M1-01~07，跑通 TC-01/TC-02

### M2 · 规则闭环 ★ 第一个真正可用的版本（1 周）
- 切片 + 索引 + 5 条硬规则 + 简易报告导出
- **产出**：上传合同 → 输出规则命中清单 → 可点击高亮 → 可导出 Markdown
- **这个里程碑就能解决真实问题了**，务必先做到这里再谈 LLM

### M3 · LLM 语义审核（1~1.5 周）
- LangGraph 编排 + 检索 + 结构化输出 + 证据校验与冲突裁决
- **产出**：语义类规则能判定了，且每条都带证据

### M4 · 人在环（1 周）
- `interrupt` 闸门 + 审阅台三栏 + 确认/驳回/新增 + 继续跑
- **产出**：真正可用的审核工作台

### M5 · 自定义规则 + 增量化（1 周）
- 文档级规则 + 重新审查 + 三层缓存 + 增量重跑
- **产出**：用户可以自己加规则并秒级看到效果

### M6 · 评测与治理（1 周）
- 30 份文档评测集 + 指标脚本 + CI 回归门禁 + trace 回放 + PII 脱敏
- **产出**：可以放心改代码了

### M7 · 生产化（1 周）
- PostgreSQL + pgvector 迁移、Nginx、脚本、监控告警、备份演练
- **产出**：可在团队内部署稳定运行

> 累计约 7~8 周（业余节奏会更长，属正常）。每个里程碑都以 `docs/modules` 对应文档的 DoD 为验收依据。

## 4. 每期的 Definition of Ready / Done

**Ready（开工前要有）**
- 对应模块文档已 review 通过
- 数据结构已定义进 `docs/03`
- 至少 3 份真实测试文档就位
- 已在 `docs/05` 矩阵中为该能力填好：**前端观测位置 + 触发方式 + 通过判据**

**Done（完成标准）——三位一体，缺一不可**
- [ ] **后端实现**：能力函数/接口完成，对应 `tests/api/test_mX_*.py` 用例通过
- [ ] **探针可见**：`/console` 中出现该能力条目并可在线触发、看到原始响应
- [ ] **业务视图可见**：在上传页/工作台/规则页等**真实页面**上能看到它的效果（不是只有 JSON）
- [ ] **用例通过**：手动清单（`docs/05` §6）中对应 TC 条目勾选，必要时补 E2E 用例
- [ ] 评测指标不低于上一期（无退化）
- [ ] README 更新了操作说明

> 三者共用同一个能力 ID（`CAP-Mx-nn`），命名约定见 `docs/05` §5。
