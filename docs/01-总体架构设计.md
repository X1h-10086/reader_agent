## 📖 白话版架构（正式图看不懂时先看这段）

**五层就是验货中心的五个车间：**

| 层 | 在干什么（白话） | 生活类比 |
| --- | --- | --- |
| L0 数据层 | 收件、拆包、把内容一件件贴上"第几页/什么位置"的标签 | 拆包台 |
| L1 表示层 | 把零散小件装箱、建目录卡，方便一秒找到 | 货架 + 目录 |
| L2 审核层 | 一半按检查清单查（便宜又准），一半问老师傅（贵但懂语义） | 清单 + 老师傅 |
| L3 裁决层 | 老师傅说的必须能指回原件；重复的合并、没依据的扔掉 | 组长复核 |
| L4 编排层 | 安排谁先做、谁和谁一起做、卡住了停下来找谁 | 施工计划表 |
| L5 交互层 | 给用户看的界面与对外接口 | 前台 |

**数据怎么走（一句白话）**：
文件进来 → 被切成**带位置的块（Block）** → 拼成**带章节的段（Chunk）** → 查清单 / 问老师傅 → 每条结论必须**挂在原文证据（Evidence）**上 → 复核定级 → 拿不准的等人 → 出报告 → 存档复盘。

## 1. 设计总则（先看这五条，其余都是推论）

| 原则 | 说明 | 违反后果 |
| --- | --- | --- |
| **P1 确定性优先** | 能用规则/代码判定的，绝不用 LLM（金额计算必须调 Calculator，不能让 LLM 口算） | 结果不可复现、成本高 |
| **P2 证据先行** | 先定位证据，再下结论；**无有效 bbox 的结论一律丢弃** | 幻觉直接外泄 |
| **P3 三层解耦** | 解析 / 规则与知识 / 编排 之间只用**结构化契约**通信 | 换解析引擎或换模型要改全局 |
| **P4 一切可回放** | 每节点留存输入快照、输出、耗时、token、模型与 prompt 版本 | 出事故无法定位 |
| **P5 人在环上，不是人在环外** | 低置信度自动挂起（`interrupt`），人给意见后继续跑 | 责任边界模糊，无法上线 |

```
┌─────────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────────┤

├─────────────────────────────────────────────────────────────────┤
│  L2 审核层     ① 规则引擎(确定性)  ② LLM 语义审核(RAG 增强)       │  M3 M4 M5
├─────────────────────────────────────────────────────────────────┤
│  L1 表示层     结构树 · 切片 · Embedding · 混合索引                │  M2 M4
├─────────────────────────────────────────────────────────────────┤
│  L0 数据层     上传 · MinerU 解析 · OCR · 存储 · 版本              │  M1 M8
└─────────────────────────────────────────────────────────────────┘
   ══ 横向贯穿：Tracing/监控(M10) · 评测集(M10) · 安全治理(M10) · 部署(M11) ══
```

**读图要点：** 数据自下而上「逐步结构化」，结论自上而下「逐步语义化」。越靠下越确定，越靠上越智能，因此**越靠上越需要证据回链来兜底**。

## 3. 一次完整审核的端到端数据流

```
① 上传 file.pdf
   │
   ▼
② M1 解析  MinerU: 预处理 → 布局分析 → (表格/公式/OCR) → 后处理 → JSON+MD
   │   产出 blocks[{type,text,bbox,page,order}] + quality_score
   ▼
③ M2 结构化 阅读顺序修正 → 标题层级树 → 语义切片 → 倒排索引 + 向量索引
   │   产出 chunks[{id, text, section_path, page, bbox, char_span}]
   ▼
④ M6 编排 加载 RuleSet(全局规则 ∪ 该文档自定义规则) → 生成执行计划
   │
   ├─ 分支 A（并行·低成本）───────────────────────────┐
   │  M3 规则引擎：缺失/正则/词典/数值/结构/冲突 → findings   │
   │  M4 检索器：混合检索(BM25+向量) → Rerank → 候选证据包    │
   │                                                        │
   └─ 分支 B（仅对语义类规则）────────────────────────┐      │
      M5 LLM 审核：证据包 + 规则 → 结构化 JSON 意见      │      │
      └→ 自校验：约束输出 + NLI 复检 + 必要证据强制引用  │      │
   │                                                        │
   ▼ 合并                                                    ▼
⑤ L3 裁决  证据回查(bbox 是否真命中) → 去重 → 冲突裁决 → 定级
   │   ┌ 阻断 blocking / 严重 major / 一般 minor / 建议 advice
   │   └ 无有效证据的 LLM 意见 → 降级或丢弃
   ▼
⑥ 置信度闸门  conf ≥ 0.85 自动通过 │ 0.5~0.85 挂起待人工 │ < 0.5 抑制
   │
   ▼
⑦ M7 人工介入（LangGraph interrupt）：确认 / 驳回 / 改等级 / 补充
   │
   ▼
⑧ M6 报告  分组 → 摘要 → 渲染 Markdown/Word/PDF + 高亮批注坐标
   │
   ▼
⑨ M8 持久化  document / chunk / finding / review_opinion / trace 全部版本化
   │
   ▼
⑩ M10 回流  人工结论 → 评测样本的黄金集 → 回归评测 → 规则/提示词迭代
```

## 4. Agent 编排状态机（LangGraph）

> 这是整个系统的"大脑"，也是项目文档 §Agent 编排 的落地形态。

```
              ┌──────────┐
              │ ingest   │  上传/格式嗅探/去重
              └────┬─────┘
                   ▼
              ┌──────────┐
              │  parse   │  MinerU → blocks[]
              └────┬─────┘
                   ▼  quality_score 不足 → ──► human_parse_check
              ┌──────────┐
              │ structure│  章节树 + 切片 + 索引
              └────┬─────┘
                   ▼
              ┌──────────┐
              │  plan    │  生成规则执行计划(哪些硬/哪些软/是否需检索)
              └────┬─────┘
                   ▼
        ┌──────────┴──────────┐   (并行扇出)
        ▼                     ▼
  ┌───────────┐        ┌────────────┐
  │rule_audit │        │ retrieve   │  混合检索 + Rerank
  └─────┬─────┘        └─────┬──────┘
        │                    ▼
        │              ┌────────────┐
        │              │ llm_audit  │  语义规则判定(工具调 Calculator/检索)
        │              └─────┬──────┘
        └──────────┬─────────┘
                   ▼
              ┌───────────┐
              │  verify   │  证据回查 / 幻觉过滤
              └─────┬─────┘
                    ▼
              ┌───────────┐
              │adjudicate │  去重·融合·冲突裁决·定级
              └─────┬─────┘
                    ▼
              ┌───────────────┐  低置信度 / 阻断级 ──► interrupt ──► human_review ──┐
              │confidence_gate│                                                     │
              └─────┬─────────┘◄────────────────────────────────────────────────────┘
                    ▼
              ┌───────────┐
              │  report   │
              └─────┬─────┘
                    ▼
              ┌───────────┐
              │  persist  │──► END (结果 + trace 落库)
              └───────────┘
```

### 状态对象（`AuditState`，全图唯一真源）

```python
class AuditState(TypedDict):
    task_id: str
    doc_id: str
    doc_type: str                 # contract | invoice | tender | generic
    blocks: list[Block]           # M1 输出，带 bbox
    chunks: list[Chunk]           # M2 输出
    plan: list[PlanItem]          # M6 计划
    rule_ids: list[str]           # 含文档级自定义规则
    candidates: list[Evidence]    # M4 候选证据
    findings: list[Finding]       # 机器产出意见
    human_ops: list[ReviewOpinion]# 人工意见
    confidence: dict[str, float]  # finding_id -> conf
    trace: list[TraceStep]        # 可回放
    budget: Budget                # token/时间预算，用于熔断
```

> **为什么用有状态图而不是顺序脚本？**
> 因为要支持：① 并行扇出（规则 vs 检索）；② 条件路由（低置信度挂起）；③ 断点续跑（人工介入后从中断点继续）；④ 单规则重审（只重跑受影响节点）。

## 5. 三类审核场景的执行配比

| 场景 | 硬规则(M3) | 检索 RAG(M4) | LLM 语义(M5) | 人工闸门默认阈值 |
| --- | --- | --- | --- | --- |
| 法务合同 | 30%（必备条款缺失、主体一致性） | 40%（法规/模板比对） | 30%（风险语义） | 0.7（较严） |
| 财务票据 | 60%（数值合计、税号格式、日期逻辑） | 10% | 30%（异常解释） | 0.8 |
| 标书公文 | 70%（章节完整性、格式要素、禁用词） | 20%（招标要求比对） | 10% | 0.85（较松） |

**可扩展性来源**：配比写在 `RuleSet` 的策略配置里，不由代码写死。新增文档类型 = 新增一份配置 + 可选解析器。

## 7. 部署视图

```
┌─────────────── 单机 / 服务器 (Linux, Docker 可选) ───────────────┐
│  Browser ──► :5173  Vite 静态资源(Nginx/DevServer)              │
│      │ HTTP / WS                                                │
│      ▼                                                          │
│  Backend :8000  FastAPI                                        │
│      ├── API: upload / task / rule / review / export            │
│      ├── LangGraph runtime（可同步执行 + 后台任务队列）          │
│      ├── Local storage: ./data/{docs,index,reports}             │
│      └── SQLite(开发) / PostgreSQL+pgvector(生产)               │
│      │ 外部依赖（二选一可切换）                                 │
│      ├── MinerU Cloud API ── 或 ── 本地 MinerU (GPU VLM 可选)   │
│      └── DeepSeek LLM API  ── 或 ── 本地推理服务                │
└─────────────────────────────────────────────────────────────────┘
```

两档模式：
- **轻量模式（推荐起步）**：MinerU Cloud API + DeepSeek API，CPU 即可，`install.sh` 无 GPU 依赖；
- **全量模式**：本地 MinerU VLM + 本地模型，需 GPU，数据完全不出内网。

## 8. 架构决策记录（ADR 摘要）

| ID | 决策 | 备选 | 选择理由 |
| --- | --- | --- | --- |
| ADR-01 | 解析用 MinerU | 自研 Pipeline / 单纯 PyMuPDF | 布局+表格+公式+OCR 一体化，且已带阅读顺序后处理，直接产出坐标 |
| ADR-02 | 编排用 LangGraph | 纯 FastAPI 顺序脚本 / Celery DAG | 需要 `interrupt` 断点做人在环，且需要状态回溯做 trace |
| ADR-03 | 前端：Vite + Vue3 | Streamlit | 需要双栏高亮/批注等精细交互，Streamlit 难做（也能做 Demo，见 M9 备选） |
| ADR-04 | 存储：SQLite → PostgreSQL | 直接上 PG | 降低起步门槛，schema 提前兼容 pgvector 字段 |
| ADR-05 | LLM：DeepSeek | OpenAI / 本地 Qwen | 成本低、中文强、兼容 OpenAI SDK，后期可无痛替换 |
| ADR-06 | 数值计算调工具 | 让 LLM 算 | LLM 算术不可靠，必须为确定性工具 |

> 完整选型理由与版本矩阵见 [02-技术选型与环境](./02-技术选型与环境.md)。
