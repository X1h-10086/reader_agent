# M3 · 规则引擎与规则管理（Deterministic Rules）

> **职责**：执行**确定性**检查，产出零成本、100% 可复现的审核意见；并让用户能在线自定义规则。
> **对应需求**：R-04（在线自定义规则 + 实时重审）、P1（确定性优先）
> **关键词**：规则 DSL、七种规则引擎、作用域（全局/文档级）、版本化、治理

---

## 1. 它在系统里的位置

项目文档把"规则与知识"列为核心技术模块之一，并强调"**企业审核离不开可配置规则引擎（版本化/审计）**"。
本模块就是这个概念的落地。**它的产出不需要 LLM，因此永远稳定、永远便宜、永远可解释**——这是整个系统可信度的地基。

> 经验法则：能用规则做的做到 70%，剩下 30% 才交给 LLM。反过来做，成本爆炸且不可控。

## 2. 七种规则引擎

| 引擎 | 判定内容 | 例子 | 实现要点 |
| --- | --- | --- | --- |
| `missing` 必备要素 | 关键词/条款是否存在 | 缺少"争议解决"条款 | 同义词组 + 语义兜底（可选向量相似度 ≥ 0.85 视为存在） |
| `regex` 正则 | 模式匹配 | 日期格式、金额格式、身份证/税号 | 预编译 + 超时保护，防灾难性回溯 |
| `dict` 词典 | 敏感词/禁用词 | "最终解释权归…" | 分级词表 + 上下文豁免列表 |
| `numeric` 数值逻辑 | 金额合计、大小写一致、比例、期限先后 | 大小写金额不一致；工期结束早于开始 | **必须调 Calculator 工具**，禁止 LLM 计算 |
| `structural` 结构 | 章节完整性、必备章节、标题层级 | 标书缺"法定代表人证明" | 依赖 M2 的 SectionTree |
| `consistency` 一致性 | 同一实体多种叫法、术语表不统一 | 合同里"甲方"忽而是 A 公司忽而是 B 公司 | 实体抽取 + 别名归并 + 章节内交叉比对 |
| `cross_ref` 交叉引用 | 引用编号是否存在、与附件是否一致 | 引用了不存在的"附件三" | 抽取引用表达式 → 校验目标存在 |

> 所有引擎统一实现 `RuleEngine.run(ctx) -> list[Finding]`，新增引擎 = 新增一个实现类 + 注册，不改调度代码。

## 3. 规则的数据表达（不写代码也能加规则）

一条规则本质上是一个 **配置对象**（见 [03 §2.3](../03-数据模型与接口契约.md)）。示例：

```json
{
  "code": "CON-007",
  "name": "合同缺少争议解决条款",
  "scope": "global",
  "engine": "missing",
  "severity": "major",
  "doc_types": ["contract"],
  "params": {
    "keywords": [["争议解决"], ["仲裁"], ["诉讼"], ["管辖"]],
    "match_logic": "any",
    "scope_path": "^\\d+\\.?\\s*争议|纠纷"    // 限定检索范围，减少误判
  },
  "message_template": "未检测到「{name}」相关条款，建议补充争议解决方式。",
  "remediation": "建议增加条款：因本合同发生争议，双方协商解决；协商不成的，提交{X}仲裁委员会仲裁。"
}
```

文档级自定义规则只是把 `"scope": "document", "document_id": "xxx"` 而已——**这就是 R-04 的实现关键：规则作用域字段**。

### 3.1 三种复杂度的用户入口

| 用户 | 入口 | 复杂度 |
| --- | --- | --- |
| 业务人员 | 表单式向导（选引擎 → 填关键词 → 选严重度） | ★ |
| 管理员 | JSON 编辑（带 schema 校验与实时预览） | ★★ |
| 开发 | 注册自定义引擎函数 | ★★★ |

⚠️ **不要一上来就做 DSL 编译器**。90% 的需求靠表单 + JSON 就能覆盖。

## 4. 执行流程

```
RuleSet(resolve: global ∪ document_scope, doc_type filter, enabled=True)
   │
   ▼
for rule in rules (并发执行，线程池 IO 密集 / 纯 CPU 用进程池):
    result = engine_registry[rule.engine].run(rule, ctx)
    # ctx = {chunks, blocks, sections, tables, full_text, calculator}
   │
   ▼
Finding(engine="rule", confidence=1.0, severity=rule.severity,
        locator=hit.chunk.locator, evidence=[Evidence(quote=摘录)])
   │
   ▼
rule.hit_count += 1 ；写入 TraceStep
```

### 4.1 为什么规则的 `confidence = 1.0`

结果确定（同输入必同输出），只存在"规则写得对不对"的问题，不存在"这次灵不灵"的问题。
若某条规则历史上误报率很高，应通过**规则治理**处理（见 §5），而不是引入假的不确定度。

### 4.2 证据怎么来

命中必须是"落在某个 Chunk 上"的，因此自动获得 `page/bbox/char_span` → 天然可高亮。
**反例**：只在全文里 `re.search` 到但没落到 chunk，必须补一次 locator 反查，否则无法高亮，不允许产出。

## 5. 规则治理（防止规则库变成垃圾场）

| 机制 | 说明 |
| --- | --- |
| 版本化 | 每次修改 `version+1`，历史任务记录当时 `rule_version`，结果可复现 |
| 命中统计 | `hit_count`、平均耗时、误报反馈数（人工 `dismiss` 计误报） |
| 下线建议 | 90 天零命中 → 标记待评审；误报率 > 40% → 强制复核 |
| 干跑预览 | `POST /rules/preview` 在样例文本上试算，避免一上线就狂炸 |
| 批量评估 | 规则改动后跑一遍评测集 diff（`before vs after`），看新增/消失多少意见 |

> **这会成为后期最重要的资产**。规则库的质量 = 产品的护城河。

## 6. 输入 / 输出契约

| 项 | 内容 |
| --- | --- |
| 输入 | `RuleSet`（含文档级自定义规则）+ M2 产物（`Chunk[]`、`SectionTree`、tables） |
| 输出 | `Finding[]`（`engine="rule"`, `confidence=1.0`, 带 `Evidence`） |
| 性能 | 300 条规则 × 100 页文档 ≤ 3s（纯本地，无网络） |

## 7. 单元验收（DoD）

- [ ] 通过 UI 新建一条文档级规则 → 点"重新审查" → 结果出现该条意见，且刷新页面仍在（持久化）
- [ ] 同一份文档 + 同一规则集跑 5 次，结果 JSON 完全一致（哈希相同）
- [ ] 数值类规则：故意把合同大小写金额改不一致，能稳定命中
- [ ] 所有产出意见都携带可高亮的 locator
- [ ] 修改规则后结果为新版本，历史任务的旧结论不被覆盖

## 8. 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| 关键词误判（"不可抗力"也算"不可"） | 大量错输出 | 允许多关键词组和 + 上下文豁免 |
| 正则在长文本上卡死 | 服务假死 | 预编译 + 单规则超时（如 200ms）+ 限制输入长度 |
| 规则爆炸不好管 | 谁也不敢删 | 治理看板 + 命名规范 `CON-001/TND-002` |
| 重新审查全量重跑太慢 | 用户等待久 | 按规则 ID 做增量重审，只重跑受影响分支（M6 支持） |
| 表格数值读不到 | 数值规则全部失效 | 优先读结构化表格 HTML，退化为文本再兜底 |

---

## 9. 学习对应

对应学习路线 **阶段 3**。动手建议：**先不要碰 LLM**，只用 Python 函数写 5 条规则（缺失/正则/数值/结构/一致性），对着 3 份文档跑到 100% 稳定。
你会得到一个重要体感：**"能确定算的就别让模型猜"**——这是所有 Agent 工程的第一性原则。
