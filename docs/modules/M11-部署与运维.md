# M11 · 部署与运维（Deployment & Ops）

> **职责**：让系统在目标环境上**一键起来、稳定运行、出问题可查**。
> **对应需求**：项目文档 §二、智能文档审核 Agent 本地部署；NFR-01（一键部署）
> **目标形态**：`./install.sh && ./start.sh` → 浏览器 `http://localhost:5173`，API `http://localhost:8000/docs`

---

## 1. 部署形态三档

| 档位 | 适用 | 组件 | 硬件 |
| --- | --- | --- | --- |
| **A 轻量（默认）** | 个人/小团队试用 | MinerU Cloud API + DeepSeek API + SQLite + Chroma | CPU 8G |
| **B 标准（推荐）** | 部门内部使用 | 后端 + PostgreSQL + pgvector + Nginx | CPU 16G |
| **C 私有化** | 数据不出内网 | 本地 MinerU VLM + 本地 LLM(vLLM) | GPU ≥ 24G |

切换方式：**只改 `.env`**（`MINERU_MODE`、`MINERU_LOCAL`、`VECTOR_STORE`、`DATABASE_URL`、LLM base_url）。这就是在 M8 做 `infra` 抽象的价值。

## 2. 目录与脚本

```
ai-document-review/
├── data/                   # 运行时数据（docs / parsed / index / reports / logs）
├── backend/                # FastAPI + LangGraph
├── frontend/               # Vite + Vue3
├── scripts/
│   ├── install.sh          # 依赖安装 + 数据目录初始化 + 依赖探活
│   ├── start.sh            # 启动后端与前端，记录 PID
│   ├── stop.sh             # 停止服务
│   └── healthcheck.sh      # 探针：端口、依赖、磁盘
├── .env / .env.example
└── docker-compose.yml      # 可选：标准档一键编排
```

```bash
# install.sh 关键步骤（示意）
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
command -v libreoffice || echo "请先安装 LibreOffice"
mkdir -p data/{docs,parsed,index,reports,logs}
cp -n .env.example .env

# start.sh 关键步骤（示意）
nohup uvicorn backend.main:app --host 0.0.0.0 --port 8000 > data/logs/backend.log 2>&1 &
echo $! > data/logs/backend.pid
cd frontend && nohup npm run dev -- --port 5173 > ../data/logs/frontend.log 2>&1 &
echo $! > ../data/logs/frontend.pid
```

Windows 用户提供 `install.ps1 / start.ps1 / stop.ps1` 同构版本（本机环境为 Windows）。

## 3. 配置与环境

必填项（缺失即启动失败并给出明确提示，而不是运行到一半报错）：

| 变量 | 说明 | 缺失时的行为 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | LLM 鉴权 | 启动即 fail-fast 并提示 |
| `MINERU_API_KEY` | 解析鉴权（云端模式） | 云端模式 fail-fast；本地模式忽略 |

**启动时自检清单**（写进 `healthcheck.sh`）：后端端口可连、`/docs` 返回 200、`.env` 必填项齐全、`libreoffice` 可执行、数据目录可写、磁盘余量 > 5G。

## 4. 运行监控

| 层级 | 指标 | 告警阈值（建议） |
| --- | --- | --- |
| 服务 | 后端可用性、5xx 率 | 5xx > 1% |
| 任务 | 解析失败率、任务卡死时长 | 失败率 > 5%；running > 30min |
| 模型 | LLM 调用失败率、P95 时延 | 失败率 > 3%；P95 > 8s |
| 检索 | 平均召回、rerank 耗时 | 召回下滑 > 5pp |
| 成本 | 单文档平均 token / 金额 | 超过基线 30% |
| 资源 | CPU / 内存 / 磁盘 | 磁盘 < 10% |

落地方式优先用最轻的：结构化日志 + 定时任务扫描 + 告警到企业微信/邮件。规模上来再上 Prometheus + Grafana。

**日志规范**：JSON 结构化，字段含 `ts, level, trace_id, task_id, node, msg`；**禁止打印完整文档正文与密钥**。

## 5. 备份与恢复

| 内容 | 频率 | 方式 |
| --- | --- | --- |
| 数据库 | 每日 | `pg_dump` / SQLite 文件快照 |
| `data/docs` 原始文件 | 每日增量 | rsync / 对象存储同步 |
| 索引 | 每周（可重建） | 允许丢失，由文件+pipeline 重建 |
| 规则库 | 每次变更自动备份 | JSON 导出版本归档 |

**恢复演练**：每季度至少做一次"从备份重建到可用"的演练，否则备份只是心理安慰。

---

## 6. 升级与回滚

- 规则/Prompt 变更：天然可回滚（版本号），历史任务仍指向旧版本；
- 应用变更：打 tag + 保留上一版本目录；数据库迁移脚本必须**向后兼容**（只加字段，分阶段删字段）；
- 索引结构变更：重建索引任务离线跑，完成后原子切换。

## 7. 单元验收（DoD）

- [ ] 干净机器上执行 `install.sh` + `start.sh`，无需手工干预即可访问前后端
- [ ] `stop.sh` 能干净停止并清理 PID
- [ ] `healthcheck.sh` 能在配置缺失时报出**准确原因**
- [ ] 服务异常退出能自动重启（systemd / docker restart policy）
- [ ] 日志为 JSON 结构化，且不包含密钥与文档正文
- [ ] 完成过一次备份恢复演练

## 8. 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| 缺 `libreoffice` 但不报错 | docx 上传后才失败 | install 探活 + 启动自检 |
| 前端 dev server 直接对外 | 性能差、无缓存 | 生产用 `npm run build` + Nginx 托管静态资源 |
| 向量库与库数据不一致 | 检索到已删除内容 | 删除操作必须同步清理索引，或用墓碑标记 |
| 磁盘被解析中间产物吃满 | 服务假死 | 定期清理 `data/tmp`，设置 TTL |
| Windows 换行符导致 sh 脚本报错 | `bad interpreter` | 仓库统一 LF，`start.ps1` 单列提供 |

## 9. 学习对应

对应学习路线 **阶段 8（交付与上线）**。动手：`install.sh` + `start.sh` + `stop.sh` 三个脚本写在别人电脑上试一次。**能不能在别人机器上跑起来，是检验工程化程度的唯一标准。**
