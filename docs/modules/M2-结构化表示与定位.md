# M2 · 结构化表示与定位（Representation & Grounding）

> **职责**：把 `Block[]` 组织成「章节树 + 语义切片 + 混合索引」，并让每一个后续结论都能回指到原文位置。
> **上游**：M1 → **下游**：M3 规则引擎、M4 检索
> **对应需求**：R-02（结构化提取 + 位置信息 + 高亮）
> **关键词**：SectionTree、Chunking、Locator、Hybrid Index

---

## 1. 为什么不能直接拿 Block 用

Block 有两个天然问题：

1. **太碎**：一个条款被标题切成 3 段，检索出来半句话，LLM 判不准；
2. **没上下文**：孤立看"甲方应在30日内付款"不知道出自哪个条款。

所以需要三层再加工：**给结构（章节树）→ 给上下文（切片）→ 给索引（可检索）**。

---

## 2. 处理流程

```
Block[] ──► ① 标题层级解析 → SectionTree
        ──► ② 语义切片 → Chunk[]（携带 section_path + 合并 bbox + char_span）
        ──► ③ 倒排索引（BM25）+ 向量索引（Embedding）
        ──► ④ Locator Service：提供 id ⇄ page/bbox/char_span 双向查询
```

---

## 3. 关键设计

### 3.1 SectionTree（章节树）

```python
@dataclass
class Section:
    id: str
    level: int            # 1~6
    title: str
    block_idx: int
    page: int
    children: list["Section"]
    path: str             # "第三章 > 3.2 > 3.2.1 违约责任"
```

构建要点：
- 优先使用 PDF **书签 outline**（最准）；无 outline 时用**字号/加粗/编号正则**推断（`第X条`、`3.2.1`、全大写短行等）；
- 推断不确定时 `level = None`，不要硬猜，交给 UI 显示为平级；
- **用途**：① 给 chunk 加 `section_path` 上下文；② 支撑"章节完整性"类结构规则（标书审核的核心）；③ 报告按章节分组输出。

### 3.2 切片策略（决定召回质量的关键）

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| **结构优先（推荐默认）** | 以二级/三级标题为边界切，超长再按段落滚动窗口二次切 | 合同、标书、制度 |
| **滑动窗口** | 固定 token + overlap（建议 512/64） | 无明显结构的文本 |
| **语义相似切分** | 相邻段落 embedding 相似度骤降处切 | 补充手段 |
| **表格/公式整块保留** | 不切，单独成 Chunk 并保留 HTML/LaTeX | 数值型规则依赖 |

通用参数建议：`target_tokens=512, overlap_tokens=64, min_tokens=64`；**禁止跨章节合并**（会让证据"串味"）。

> **坑**：不要把标题单独切成一块且丢弃其 `section_path`。正确做法是标题文本**拼进该节所有 chunk 的前缀**，形如：
> `[3.2.1 违约责任] 甲方未在约定期限内履行...`

### 3.3 Chunk 必须携带的可回溯信息

```python
Chunk(id, block_ids=[12,13], text=..., section_path=...,
      page=7, bbox=[0.12,0.31,0.88,0.42], char_span=(12450,13002), index_in_doc=33)
```

- `block_ids`：回原始块（表格 HTML 还能找回）；
- `bbox`：合并块的最小包围盒（用于整段高亮）；
- `char_span`：**M5 反幻觉校验的最快检测通道**（字符串比对，毫秒级）。

### 3.4 混合索引

| 索引 | 负责召回 | 优势场景 |
| --- | --- | --- |
| BM25 倒排 | 精确词、条款号、金额数字、主体名 | "第 8.3 条"、"汇率为 6.5" |
| 向量索引 | 语义近似表达 | "违约责任" ≈ "违反本合同的责任承担" |
| 元数据过滤 | `page / section / block.type` | 限定在某章节或只查表格 |

统一入口：

```python
def retrieve(query: str, top_k=20, filters=None) -> list[Candidate]:
    bm25_hits  = bm25_index.search(query, 50)
    vec_hits   = vector_index.search(embed(query), 50)
    merged     = rrf_fusion([bm25_hits, vec_hits], k=60)   # Reciprocal Rank Fusion
    reranked   = reranker.rank(query, merged)[:top_k]
    return reranked
```

> RRF 融合不需要调权重，比"加权求和"稳得多，起步首选。

### 3.5 Locator Service（高亮的最后一公里）

```
finding_id ─► evidence.chunk_id ─► Chunk.bbox/page ─► 前端坐标换算 ─► pdf.js 高亮层
```

坐标换算：`px = bbox_norm * page_width * (zoom)`。为兼容扫描件旋转，需记录 `page_rotation`。

## 5. 单元验收（DoD）

- [ ] 任取一个 Chunk，能在 UI 上精确高亮出它的原文区域；
- [ ] SectionTree 在带书签 PDF 上与使用 bookmark 的结果对比，层级准确率 ≥ 90%；
- [ ] "第 8.3 条" 这样的精确查询 BM25 能排第一；"谁承担违约责任" 这类模糊查询向量能进前 5；
- [ ] 表格块不被切碎，且 `meta.html` 保留；
- [ ] 索引可复用：二次审核同一版本不重复建索引。

---

## 6. 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| 切片过短 | LLM 只见半句，误判多 | 提高 target_tokens，强制携带 section_path 前缀 |
| 跨章节混合 | 证据看似相关实则来自无关章节 | 禁止跨标题边界合并 |
| 表格丢结构 | 数值规则无法校验合计 | 表格单独成 chunk + 保留 HTML |
| 重复 embedding 开销 | 每次重审都烧钱 | 按 `version + chunk_params` 做缓存键 |
| 高亮偏移 | 位置对不上 | 检查是否已归一化、是否用了同一份页面尺寸、是否忽略 rotation |

## 7. 学习对应

对应学习路线 **阶段 2**。动手建议：把你自己写的一份合同丢进去，在页面上做三件事——
① 看章节树对不对；② 点击一个 chunk 看它高亮到哪；③ 故意用模糊词检索，看能不能召回。**这三步做完，你就懂了 RAG 里 90% 的工程质量问题来源。**
