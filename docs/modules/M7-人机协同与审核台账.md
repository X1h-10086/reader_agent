# M7 · 人机协同与审核台账（Human-in-the-Loop）

> **职责**：让人工审阅成为**一等公民流程**，并把人工结论沉淀为可复用的资产。
> **对应需求**：R-03（人工随时介入并给出审核意见）
> **关键词**：三态结论、审阅动线、意见同源、样本回流、二次学习

---

## 1. 位置：人机协同不是一个 UI，是一套闭环

很多人以为"人机交互"就是给人看个列表。**真正重要的是闭环：**

```
机器产出(疑点) → 人判断(确认/驳回/修正/新增) → 结论入库 → 回流为样本 → 评测与规则优化 → 机器变准
                                                   ↑                                  │
                                                   └────────── 下一轮更准 ────────────┘
```

少了后半段的系统在三个月后一定会退化成"看起来聪明但没人信"的摆设。

---

## 2. 人工意见的四种动作

| 动作 | 含义 | 对结果的影响 | 回流价值 |
| --- | --- | --- | --- |
| `confirm` 确认 | 机器说得对 | status → confirmed，进报告 | 正样例↑，提升该规则置信权重 |
| `dismiss` 驳回 | 误报 | status → dismissed，不进报告 | **负样例**，用于调规则/阈值（最有价值） |
| `modify` 修正 | 结论对但级别/措辞不对 | 更新 severity / content | 用于校准定级标准 |
| `add` 新增 | 机器没发现的问题 | 新增 finding，engine=human | **补召回**，用于新增规则或补评测样例 |

> **设计要点**：人工意见与机器意见必须是**同一种数据结构**（`Finding`），只是 `engine` 字段不同。这样报告、导出、统计全部复用同一条链路。

---

## 3. 审阅动线（UI 层面的三条动线，实现见 M9）

1. **快速扫雷**：按 severity 排序，先处理 blocking → major；支持键盘 `Y/N/空格` 快速确认。
2. **证据对照**：左原文（高亮定位）右意见；点击证据自动滚动并高亮到对应位置。
3. **统一处理**：批量确认同类问题、批量导出、一键生成修订清单。

**体验三原则**：
- 每条意见必须**一键跳到原文**（否则用户无法判断，只会全部忽略）；
- 必须能**一键驳回**（否则误报永远清理不掉）；
- 必须显示**这条意见来自哪个规则/哪个模型**（否则用户无法建立信任）。

---

## 4. 审核台账

| 维度 | 内容 | 用途 |
| --- | --- | --- |
| 任务台账 | 谁审的、审了多久、多少意见、多少被确认 | 绩效考核与效率度量 |
| 规则台账 | 每条规则的命中率、误报率、平均处理时长 | 规则治理（M3 §5） |
| 意见台账 | 历史所有 finding 与人工结论，可按条款语义检索 | **下次遇到相似条款直接给历史结论** |
| 变更台账 | 谁在什么时候改了哪条规则 | 审计与回溯 |

---

## 5. 回流与"越用越准"的两个抓手

### 5.1 抓手段一：历史相似条款提示（低成本，见效快）
人工确认过的 finding，把它的 `text + section_path + rule_code + 结论` 写入 `kb_case`（M4 `kb_case` 集合）。
下次审核相似条款时自动检索出来，在意见里加一行：

> 📌 历史上 2026-04-12 在《XX 合同》中同类条款被认定为 major，处理建议：……

这一步几乎零成本，但会让用户明显感觉"它记住了"。

### 5.2 抓手段二：负样例沉淀
所有 `dismiss` 的意见进入评测集的**负样例**区：
- 若同一规则被驳回 ≥ 5 次 → 自动创建规则复核任务；
- 每次调规则/改 Prompt 后，必须跑一遍回归，看误报是否下降（M10）。

> ⚠️ **不要一上来就做"微调模型"**。规则优化 + Prompt 优化 + RAG 优化这三板斧能把准确率提升一大截，成本却低得多。微调留到规则/Prompt 都调到瓶颈之后。

## 6. 输入 / 输出契约

| 项 | 内容 |
| --- | --- |
| 输入 | `task_id`、`finding_id`、人工动作与评论 |
| 输出 | `ReviewOpinion` + 更新后的 `Finding.status` + 回流事件 |
| 接口 | `POST /tasks/{id}/findings/{fid}/review`、`POST /tasks/{id}/findings`、`POST /tasks/{id}/resume` |

---

## 7. 单元验收（DoD）

- [ ] 人工新提出的问题与机器意见在同一份报告里，且同样带高亮定位
- [ ] 每个动作都能在台账里查到操作人与时间
- [ ] 驳回的意见不会出现在最终导出报告中
- [ ] 一条意见被驳回后，相同规则在另一份文档的相同表述上不会重复报（回流生效）
- [ ] 可导出"本次审核统计"（确认率/误报率）

---

## 8. 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| 人工意见单独一张表、单独一套展示逻辑 | 代码翻倍、体验割裂 | 与机器意见同构共存（只差 `engine` 字段） |
| 只记录"最终结论"，丢掉"曾经报错过什么" | 无法评估遗漏 | 保留全量 finding + status，不物理删除 |
| 没有驳回入口 | 误报堆积，用户放弃使用 | 驳回是必备动作，UI 上要一眼可见 |
| 硬塞交互式建议让用户等 | 阻塞感强 | 人在环只在低置信度触发，且支持跳过 |
| 回流数据没做脱敏 | 合规风险 | 入 `kb_case` 前做 PII 脱敏（M10） |

---

## 9. 学习对应

对应学习路线 **阶段 6（人机闭环）**。动手做一件小事就够了：
**给每条机器意见加上"确认/驳回"两个按钮，并把驳回记录落库。** 然后观察一周——你会惊讶地发现，光是把驳回数据攒起来，就能指导你把准确率提升一大截。
