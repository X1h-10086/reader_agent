# M4 · 知识库与混合检索（Knowledge & Retrieval）

> **职责**：把法规、制度、模板、历史案例变成**可检索、可引用**的知识源，为 LLM 审核提供外部依据。
> **对应需求**：R-09/R-10（语义规则与知识挂载）、项目文档 §"混合检索+重排序提升命中与可溯源性"
> **关键词**：知识集合分域、Hybrid Retrieval、Rerank、引用格式、知识版本

---

## 1. 为什么需要知识库

LLM 知道"常识性的合同知识"，但不知道：

- 你们公司**最新版的合同管理办法**；
- 本行业**特定监管口径**；
- 去年那份**被法务否掉的相似条款**；
- 你自己维护的**标准条款模板**。

这些东西在模型训练数据里没有。**没有知识库，LLM 只能凭"通用直觉"审核 → 结论似是而非 → 无法在专业场景落地。**

---

## 2. 知识分域（不要一个大杂烩）

| 集合 | 内容 | 特点 | 更新频率 |
| --- | --- | --- | --- |
| `kb_law` | 法律法规、部门规章 | 权威、需精确到条 | 低（月/季） |
| `kb_policy` | 企业内控制度、管理办法 | 权威、强版本性 | 中 |
| `kb_template` | 标准条款模板、示范文本 | 用于"比对差异" | 低 |
| `kb_case` | 历史审核案例与人工批注 | 经验性，含金量最高 | 高（随审核产出自动沉淀） |
| `kb_faq` | 常见问答/口径解释 | 短文本，用于消歧 | 中 |

**为什么要分域**：检索时用 `kb_sources` 过滤（每条规则显式声明依赖哪些集合），能显著降低噪声。例如"必备条款"规则只查 `template + policy`，不会被法条冲淡。

---

## 3. 知识入库流程

```
源文件(pdf/doc/md/html)
   │
   ├─① 解析（复用 M1/M2 的同一套管线！）
   ├─② 切分：法规按"条"切（★ 法律文本的最小引用单位是"条"）
   ├─③ 元数据抽取：law_name, article_no, effective_date, version, source_url, authority
   ├─④ 生成 chunk_text = 「标题路径 + 正文」并 embed
   └─⑤ 写入向量库 + BM25 索引，记录 kb_domain 便于过滤
```

### 3.1 法规切片的特殊之处

法规**不能按固定 token 切**，否则一条可能被拦腰截断，引用时变成"第 30 条（半句）"，用户无法核对。
正确做法：以 `第X条` 为原子单位；超长条（如长列表）再按款 `(一)(二)` 二级切，但保留条号前缀。

### 3.2 元数据是可用性的关键

```python
KbChunkMeta = {
  "kb_domain": "law",
  "source_id": "民法典",
  "article_no": "第五百八十五条",
  "effective_date": "2021-01-01",
  "version": "2020修订",
  "source_url": "http://...",   # ★ 便于用户点开核对
}
```

引用时必须渲染成：`《民法典》第五百八十五条。……（来源链接）`。
**能否点开原文核对，决定用户是否相信你的系统。**

## 4. 检索链路

```
query ──┬─► BM25 top50 ──┐
        └─► Vector top50 ┴─► RRF 融合 ──► Rerank ──► top_k(3~8) ──► 证据包 EvidencePack
                                     ▲
                                     └─ 过滤：kb_domain / effective_date / version
```

```python
class EvidencePack(BaseModel):
    query: str
    items: list[Candidate]        # 每条含 quote, source_id, score, locator/url
    dropped: list[str]            # 被去重/过滤掉的，用于调试
```

**关键参数建议**

| 参数 | 建议值 | 理由 |
| --- | --- | --- |
| 融合 top-n | 50 + 50 | 给 Reciprocal Rank Fusion 足够候选 |
| Rerank 后 | 5~8 条 | 更多反而稀释注意力，且烧 token |
| 相似度阈值 | cosine ≥ 0.35 | 低于阈值宁愿不用，避免塞噪声给 LLM |
| 同源去重 | 相邻重复度 > 0.9 只留最高分 | 防止同一条款重复占满窗口 |

## 5. 检索在审核中的三种用法

| 用法 | 说明 | 触发规则 |
| --- | --- | --- |
| **证据检索** | 找出文档中与该规则相关的原文片段 | 所有 `llm` 引擎规则的**前置步骤** |
| **依据检索** | 找出支持"为什么这条有问题"的外部条文 | `rule.retrieve_required = true` |
| **模板对比** | 检索标准条款，与文档条款逐项 diff | 合同/标书类文档的结构化规则 |

> ⚠️ **顺序很重要**：必须先有"文档内证据"，再谈"外部依据"。只有外部依据没有文档证据，等于在说"法律规定应该有 X"，但没证明"这份文档里没有 X"——这是最常见的逻辑漏洞。

## 6. 输入 / 输出契约

| 项 | 内容 |
| --- | --- |
| 输入 | `query`（由规则生成，可用 LLM 改写扩写）、`kb_sources`、`filters`、`top_k` |
| 输出 | `EvidencePack`（候选带来源、分数、可点击溯源信息） |
| SLO | 单次检索 ≤ 300ms（含 rerank） |

查询词怎么来（三种由简到繁）：
1. **规则内置关键词**（最快，先做）；
2. **模板拼装**：`"{rule.keywords} {doc_type} {section_path}"`；
3. **LLM 查询改写**（`query rewriting`，多路召回后再融合，准确率最高，成本也最高）。

## 7. 单元验收（DoD）

- [ ] 至少灌入 1 个领域的知识（≥ 50 条），可按条检索命中
- [ ] "禁止转包" 类查询能同时召回（a）文档原文片段（b）法条依据
- [ ] 检索结果每条都能点开原文/原始链接核对
- [ ] 检索命中率在自建 30 问评测集上 Recall@5 ≥ 85%
- [ ] 知识更新（新增一部制度）不影响旧任务结果的历史可复现性（版本隔离）

## 8. 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| 固定长度切坏法条 | 引用不完整 | 按条切 + 条号前缀 |
| 只做向量检索 | 条款号、金额、主体名搜不到 | 必须混合检索（BM25） |
| 知识过期未更新 | 引用废止条款给出错误意见 | 元数据带生效日期 + 定期巡检任务 |
| 检索把噪声喂给 LLM | 结论被带偏 | 相似度阈值 + rerank + 限制 top_k |
| 知识库与文档库混在一个索引 | 互相污染 | 物理分集合 + 检索时显式指定 domain |

## 9. 学习对应

对应学习路线 **阶段 4**。建议动手顺序：
① 只用 BM25 搜一把，看精确词有多强；
② 只用向量搜一把，看语义近似有多强；
③ 融合 + rerank，对比三者 Recall@5 的差异。**亲手测出这个差距，你就理解了 RAG 的全部价值与全部局限。**
