# M1 · 文档接入与解析（Ingestion & Parsing）

> **职责**：把任意格式的"文件"，变成机器可消费且**带坐标**的结构化单元 `Block[]`。
> **上游**：用户上传 → **下游**：M2 切片与索引
> **对应需求**：R-01（多格式解析）、A-04/A-05（MinerU）
> **对应的系统原则**：P3 分层解耦、P4 可回放

---

## 1. 这个模块为什么最容易被低估

项目文档强调"**对于文档的精准解析是文档审核类 Agent 落地的关键**"。原因是：

```
解析错了 → 切片错位 → 检索召回不到 → LLM 没证据 → 要么漏检要么幻觉
```

**解析是整个系统的误差源放大器**。上层做的所有聪明事，都建立在 blocks 是对的这件事上。
因此本模块的两个硬性产物：**① 结构化 Block[]；② 一个诚实的 `quality_score`**。

---

## 2. 处理流程

```
upload(file)
  │
  ├─① 校验：类型白名单 / 大小上限 / 病毒扫描(可选) / sha256 去重
  │
  ├─② 格式归一化
  │     pdf ──────────────► 直连 MinerU
  │     doc/docx/ppt/pptx ► LibreOffice headless → pdf → MinerU
  │     png/jpg/jpeg ─────► MinerU OCR 链路
  │     md/txt ───────────► 轻量自解析 → Block[]（跳过 MinerU）
  │
  ├─③ MinerU 解析（Pipeline 默认）
  │     预处理 → 布局分析 → 表格/公式识别 → OCR(若扫描件) → 后处理（重叠修复+阅读顺序）→ JSON
  │
  ├─④ 适配层 Adapter（★ 必做）
  │     外部字段 → 内部统一 Block 结构；坐标归一化 [0,1]
  │
  ├─⑤ 质量评估 → quality_score ∈ [0,1]
  │
  └─⑥ 落库 + 事件通知（WS）→ 交给 M2
```

## 3. 关键设计

### 3.1 适配器模式（隔离外部变化）

> **不要用 MinerU 的返回结构作为内部契约。** 它一升级，你的数据库和前端全崩。

```python
# parsing/adapters/base.py
class BaseAdapter(Protocol):
    def to_blocks(self, raw: dict) -> list[Block]: ...

# parsing/adapters/mineru.py      云端/本地 MinerU
# parsing/adapters/markdown.py    简单文本
# parsing/adapters/docx.py        可选：绕过 LO 的直解析
```

内部 `Block` 结构见 [03-数据模型](../03-数据模型与接口契约.md) §2.1。坐标**必须归一化**：

```python
def normalize(bbox, page_w, page_h):
    x0, y0, x1, y1 = bbox
    return [x0/page_w, y0/page_h, x1/page_w, y1/page_h]
```

### 3.2 阅读顺序的重要性

MinerU 后处理已做按人类阅读顺序重排。**不要自作聪明按 bbox 的 y-x 排序覆盖它**——多栏文档的正确答案是"先左栏从上到下，再右栏"。若确需自定义排序，仅作为备用字段，不覆盖 `idx`。

### 3.3 双模式与自动降级

| 触发条件 | 动作 |
| --- | --- |
| 默认 | Pipeline 模式解析 |
| `quality_score < 0.6` 且开启了 GPU 模式 | 自动切换 VLM 重解析一次 |
| 两次都低 | 任务进入 `waiting_human`，提示"文档质量差，请人工确认"，并在前端给出原始 PDF 对照视图 |

这样：**常规文档省资源，疑难杂症保质量**，且成本可控。

### 3.4 质量评分怎么算（务实版）

不要追求完美，用几个便宜的启发式信号加权即可：

```python
score = 0.4 * ocr_ratio_ok          # 非扫描件：1.0；扫描件：OCR 平均置信度
      + 0.2 * has_outline_ratio     # 识别到标题层级/目录的比例
      + 0.2 * text_density_ok       # 每页字符数在合理区间（太少=漏字，太多=粘连）
      + 0.1 * table_parse_ok        # 表格能否被解析为结构化（表格页占比 vs 成功数）
      + 0.1 * language_match        # 检测语言是否符合预期
```

把**分项的明细存进 `meta.quality_detail`**，用户问"为什么说我文档质量差"时能给答案。

### 3.5 异步与幂等

- 解析耗时可达分钟级，必须走后台任务：`POST /documents/{id}/parse` 立刻返回 `task_id`，进度走 WebSocket。
- 同一 `file_hash` 已解析过则直接复用（**幂等**），避免重复烧 MinerU 额度。

## 4. 输入 / 输出契约

| 项 | 内容 |
| --- | --- |
| 输入 | `file: bytes`, `doc_type`, `mode: pipeline｜vlm` |
| 输出 | `DocumentVersion`（含 `quality_score`） + `Block[]` + `full_text` + `char_span` 映射表 |
| 失败 | 抛 `ParseError`（码 2001），记录 `TraceStep`，前端展示 `trace_id` |

**`char_span` 是高分项**：为每个 block 记录在 `full_text` 中的字符区间，后续 M5 校验"这段话是不是真的来自原文"时可直接用字符串比对，无需再依赖坐标，又快又准。

## 5. 单元验收（DoD）

- [ ] `.pdf / .docx / .pptx / .png` 四种格式各一份样例能成功解析出 `Block[]`
- [ ] 每个 Block 都有 `page + bbox(归一化) + char_span`
- [ ] 前端能在原 PDF 上按 bbox 精确高亮到对应段落（±3px 内）
- [ ] 多栏 PDF 的阅读顺序正确（人工肉眼检查前 2 页）
- [ ] 同一文件上传两次不重复解析（命中缓存）
- [ ] 一份故意弄花的扫描图能被识别为低质量并给出降级提示

## 6. 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| Windows 中文路径 | OCR/转换报编码错 | 中间产物统一 `data/tmp/<uid>` 英文路径 |
| LibreOffice 未装 | docx 转换失败却不报原因 | install 脚本检测 + 启动时探活，明确报错 |
| 页眉页脚混入正文 | 干扰后续检索与判定 | 按重复出现 + 页面上下 10% 区域识别为 header/footer，默认降权（可在规则里显式启用） |
| 表格被拆成多行 text | 数值类规则失效 | 保留 `type=table` 与 `meta.html`，M3 数值规则优先消费结构化表格 |
| 超大文件（>500页） | 超时 | 分页批处理 + 进度上报；必要时先抽一级再做全文 |

## 7. 与你学习的对应

本模块对应学习路线的 **阶段 2（解析与结构化）**。你需要亲手做的事：

1. 跑通 MinerU 的官方 Demo，观察 JSON 输出里每个字段的含义；
2. 写一个 `mineru_adapter.py`，把它的输出转成你自己的 `Block`；
3. 用 pdf.js 在页面上把 `Block[]` 画出来——**当你亲眼看到高亮框对准段落时，你就理解了"证据"二字的工程含义**。
